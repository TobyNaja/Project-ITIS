# บทที่ 1 บทนำ

## 1.1 ที่มาและความสำคัญของปัญหา

องค์กรขนาดเล็กถึงขนาดกลางจำนวนมากใช้ firewall และระบบตรวจจับการบุกรุก (Intrusion Detection System: IDS)
แบบ open source เช่น pfSense และ Suricata เป็นแนวป้องกันหลักของเครือข่าย ระบบเหล่านี้สามารถตรวจจับ
เหตุการณ์ที่น่าสงสัยและสร้างการแจ้งเตือน (alert) ได้อย่างต่อเนื่อง แต่ IDS ทำหน้าที่ "ตรวจจับ" เท่านั้น
การตอบสนองต่อเหตุการณ์ เช่น การสั่ง firewall ให้ปิดกั้น (block) แหล่งที่มาของการโจมตี ยังต้องอาศัยผู้ดูแลระบบ
ตัดสินใจและดำเนินการด้วยมือ ในองค์กรที่มีบุคลากรด้านความปลอดภัยจำกัดและไม่มีศูนย์ปฏิบัติการด้านความปลอดภัย
(Security Operations Center: SOC) การตอบสนองจึงขึ้นอยู่กับว่าผู้ดูแลระบบเห็น alert เมื่อใดและมีเวลาดำเนินการหรือไม่

การนำการตอบสนองแบบอัตโนมัติมาใช้ช่วยให้ firewall ตอบสนองได้โดยไม่ต้องรอการตัดสินใจของมนุษย์ แต่ก็มีความเสี่ยง
ในตัวเอง alert เพียงรายการเดียวอาจเป็นผลบวกลวง (false positive) หากระบบปิดกั้นทุกครั้งที่เห็น alert
อาจกระทบการใช้งานปกติของเครือข่าย การปิดกั้นอัตโนมัติจึงต้องมีกลไกควบคุมความปลอดภัย (safety control)
มีการบันทึกเหตุผลของการตัดสินใจที่ตรวจสอบย้อนหลังได้ (audit) และต้องย้อนกลับได้ (reversibility)

นอกจากนี้ การตอบสนองอัตโนมัติจะทำงานได้ก็ต่อเมื่อ IDS ยังทำงานอยู่ หาก Suricata หยุดทำงานหรือไม่เขียน
เหตุการณ์ออกมา ระบบที่อยู่ปลายทางจะไม่ได้รับข้อมูลใดเลย และความเงียบของเครือข่ายอาจถูกตีความผิดว่าไม่มีภัยคุกคาม
การตรวจสอบสุขภาพเชิงการทำงาน (functional health) ของ IDS และการกู้คืนบริการจึงเป็นส่วนหนึ่งของปัญหาเดียวกัน

โครงงานนี้จึงพัฒนาต้นแบบ (prototype) ของระบบตอบสนองต่อเหตุการณ์ด้านความปลอดภัยแบบอัตโนมัติ ที่รวมเหตุการณ์
หลายรายการเข้าเป็นรูปแบบ (event correlation) ประเมินความเสี่ยงด้วยแบบจำลองแบบถ่วงน้ำหนัก ตัดสินใจด้วยกฎที่กำหนด
ไว้ล่วงหน้า สั่ง firewall ปิดกั้นชั่วคราวพร้อมตรวจสอบว่าการปิดกั้นมีผลจริง และกู้คืน IDS เมื่อทำงานผิดปกติ
แล้วประเมินระบบด้วยการทดลองในสภาพแวดล้อมห้องปฏิบัติการที่ควบคุมได้

## 1.2 ปัญหาของระบบเดิม (Problem Statement)

1. **IDS ตรวจจับได้ แต่การตอบสนองต้องพึ่งการดำเนินการของผู้ดูแลระบบ** ทำให้การปิดกั้นแหล่งที่มาของการโจมตี
   ล่าช้าและขึ้นกับความพร้อมของบุคลากร
2. **alert เดี่ยวอาจเป็นผลบวกลวง** การตอบสนองแบบ "1 alert = 1 block" จึงไม่เหมาะสม
   การตัดสินใจควรพิจารณารูปแบบของเหตุการณ์หลายรายการ เช่น ความถี่ ช่วงเวลา และความรุนแรง จากแหล่งที่มาเดียวกัน
3. **การปิดกั้นอัตโนมัติที่ไม่มีกลไกควบคุมเป็นอันตรายต่อการใช้งาน** ต้องมีวิธีป้องกันไม่ให้แหล่งที่มาที่เชื่อถือได้
   ถูกปิดกั้น มีการยืนยันว่าคำสั่งมีผลจริง (การสั่งสำเร็จไม่เท่ากับการบังคับใช้สำเร็จ) มีการยกเลิกการปิดกั้นเมื่อครบเวลา
   และมีบันทึกที่อธิบายได้ว่าปิดกั้นใคร เพราะอะไร ด้วยกฎใด
4. **ความเงียบของเครือข่ายไม่ได้หมายความว่า IDS ทำงานปกติ** จำเป็นต้องตรวจสุขภาพของ IDS จากผลลัพธ์ที่มันผลิต
   ไม่ใช่แค่ตรวจว่า process ยังอยู่ และต้องกู้คืนได้ภายในจำนวนครั้งที่จำกัด

## 1.3 คำถามวิจัย (Research Question)

> *Can rule-based correlation of IDS events reduce the time required to enforce a predefined firewall
> response in a controlled network environment?*

(การเชื่อมโยงเหตุการณ์จาก IDS ด้วยกฎ สามารถลดเวลาที่ใช้ในการบังคับใช้การตอบสนองของ firewall ที่กำหนดไว้
ล่วงหน้า ในสภาพแวดล้อมเครือข่ายที่ควบคุมได้ หรือไม่)

โครงงานนี้ตอบคำถามวิจัยโดย**วัดเวลาของเส้นทางการตอบสนองอัตโนมัติ** ตั้งแต่เหตุการณ์ถูกสร้างขึ้น ผ่านการตรวจจับ
การตัดสินใจ จนถึงเวลาที่ยืนยันได้ว่า firewall บังคับใช้การปิดกั้นแล้ว (end-to-end response time) พร้อมกับวัดความสำเร็จ
ของการตอบสนองที่กำหนดไว้ล่วงหน้าในแต่ละสถานการณ์ทดสอบ โครงงานไม่ได้วัดเวลาการตอบสนองของผู้ดูแลระบบที่ทำด้วยมือ
เพื่อนำมาเปรียบเทียบ เพราะการวัดการทำงานของมนุษย์อย่างเที่ยงตรงในห้องปฏิบัติการทำไม่ได้ ขอบเขตของโครงงาน
จึงกำหนดให้ใช้ end-to-end latency ของระบบอัตโนมัติแทนการเปรียบเทียบระหว่างการตอบสนองด้วยมือกับแบบอัตโนมัติ
(หัวข้อ 1.5)

## 1.4 วัตถุประสงค์ของโครงงาน

**ตาราง 1.1** วัตถุประสงค์ของโครงงาน

| รหัส | วัตถุประสงค์ |
|---|---|
| O1 | รับเหตุการณ์ด้านความปลอดภัย (security event) จาก Suricata ในรูปแบบ EVE JSON |
| O2 | เชื่อมโยงเหตุการณ์ (event correlation) ตาม source IP, ช่วงเวลา (time window), ความถี่ และความรุนแรง |
| O3 | พัฒนาแบบจำลองการประเมินความเสี่ยงแบบถ่วงน้ำหนัก ที่อ้างอิงแนวคิดจากมาตรฐานด้านความปลอดภัย (standard-informed) |
| O4 | พัฒนาการตอบสนองอัตโนมัติด้วยกฎ (rule-based automated response) |
| O5 | เชื่อมต่อกับ pfSense เพื่อปิดกั้นแหล่งที่มาชั่วคราว (temporary block) |
| O6 | ยกเลิกการปิดกั้นอัตโนมัติเมื่อครบเวลา (auto-unblock) |
| O7 | ตรวจสอบว่า firewall บังคับใช้การปิดกั้นจริง (command success ≠ enforcement success) |
| O8 | สร้างกลไกความปลอดภัยแบบ allowlist |
| O9 | สร้างบันทึกการตรวจสอบ (audit trail) ที่อธิบายเหตุผลของการตัดสินใจได้ |
| O10 | กู้คืนการทำงานของ Suricata เชิงฟังก์ชัน โดยลองใหม่ไม่เกิน 3 ครั้ง |
| O11 | วัดประสิทธิภาพของระบบ: latency, อัตราการปิดกั้นที่ไม่จำเป็นภายใต้สถานการณ์ทดสอบ, overhead และ sensitivity ของแบบจำลองความเสี่ยง |

## 1.5 ขอบเขตของโครงงาน

### 1.5.1 ผู้ใช้เป้าหมาย

ผู้ดูแลระบบเครือข่ายหรือระบบคอมพิวเตอร์ขององค์กรขนาดเล็กถึงขนาดกลาง ที่ใช้ firewall และ IDS แบบ open source
(pfSense และ Suricata) แต่มีบุคลากรด้านความปลอดภัยจำกัดและไม่มี SOC

### 1.5.2 องค์ประกอบในขอบเขต

| องค์ประกอบ | บทบาท |
|---|---|
| Suricata | ตรวจจับเหตุการณ์ (IDS) และส่งออกเป็น EVE JSON |
| pfSense | บังคับใช้การปิดกั้นและยกเลิกการปิดกั้น (firewall enforcement) |
| Python security engine | เชื่อมโยงเหตุการณ์, ประเมินความเสี่ยง, ตัดสินใจด้วยกฎ, สั่งการ firewall และกู้คืน IDS |
| SQLite | บันทึกการตรวจสอบ (audit trail) |
| Prometheus และ Grafana | monitoring และแสดงผลข้อมูลโครงสร้างพื้นฐาน (เป็นหลักฐานเท่านั้น ไม่ใช่ข้อมูลนำเข้าของการตัดสินใจ) |
| เครื่องทดสอบ (test host) | สร้างทราฟฟิกและเหตุการณ์ทดสอบที่ควบคุมได้ |

ขอบเขตเชิงฟังก์ชันประกอบด้วย การเชื่อมโยงเหตุการณ์แบบใช้กฎภายในช่วงเวลา 10 วินาที (ปรับค่าได้), การประเมินความเสี่ยง
แบบถ่วงน้ำหนักพร้อมการวิเคราะห์ความไว (sensitivity analysis) ของชุดน้ำหนัก, การปิดกั้นชั่วคราว 300 วินาที
(เป็นพารามิเตอร์ของการทดลองที่ปรับค่าได้), allowlist ที่มีผลเหนือการปิดกั้น และการตรวจสุขภาพเชิงฟังก์ชันของ Suricata

โครงงานกำหนด Prometheus และ Grafana เป็นองค์ประกอบสำหรับการ monitoring และการนำเสนอข้อมูล
อย่างไรก็ตาม ในการทดลองของโครงงานนี้ส่วนดังกล่าวไม่ได้ถูกติดตั้ง จึงไม่ได้ใช้สำหรับการวัด overhead

เครื่องทดสอบมีบทบาทเป็นแหล่งทราฟฟิกทดสอบที่ควบคุมได้ แต่ชุดข้อมูลหลักของการทดลองสร้างจากการป้อนเหตุการณ์
EVE ที่ควบคุมได้ (controlled EVE injection) เพื่อให้ทราบเวลาที่เหตุการณ์เกิดขึ้นอย่างแม่นยำ (รายละเอียดในบทที่ 5)

### 1.5.3 นอกขอบเขต

- Machine learning / deep learning
- Threat intelligence feed
- แพลตฟอร์ม SIEM/SOC ระดับองค์กร
- Distributed firewall หรือ Kubernetes
- การติดตั้งใช้งานจริง (production deployment) และการ hardening
- การตรวจจับ zero-day และการวิเคราะห์มัลแวร์ขั้นสูง
- การปิดกั้นแบบปรับระยะเวลาเพิ่มขึ้น (adaptive/escalating blocking) — เป็นงานในอนาคต
- การใช้ CPU/RAM/PPS เป็นข้อมูลนำเข้าของคะแนนความเสี่ยง — ใช้เป็นหลักฐานเท่านั้น
- การเปรียบเทียบเวลาตอบสนองระหว่างการทำด้วยมือกับแบบอัตโนมัติ — ใช้ end-to-end latency แทน

## 1.6 ประโยชน์ที่คาดว่าจะได้รับ

1. ได้ต้นแบบระบบที่เชื่อม IDS กับ firewall ให้ตอบสนองต่อรูปแบบเหตุการณ์ที่กำหนดได้โดยอัตโนมัติ
   สำหรับสภาพแวดล้อมที่ใช้ pfSense และ Suricata
2. ได้แนวทางการตอบสนองอัตโนมัติที่มีกลไกความปลอดภัย ได้แก่ การเชื่อมโยงเหตุการณ์ก่อนตัดสินใจ, allowlist,
   การตรวจสอบการบังคับใช้, การยกเลิกการปิดกั้นตามเวลา และ audit trail ที่อธิบายเหตุผลได้
3. ได้ข้อมูลเชิงปริมาณเกี่ยวกับเวลาของแต่ละช่วงในเส้นทางการตอบสนองอัตโนมัติ (ตรวจจับ ตัดสินใจ และบังคับใช้)
   ภายใต้สภาพแวดล้อมที่ควบคุมได้
4. ได้กลไกตรวจสุขภาพเชิงฟังก์ชันและกู้คืน IDS ที่มีจำนวนครั้งการลองใหม่จำกัด
5. ได้กรณีศึกษาการวิเคราะห์ความไวของแบบจำลองความเสี่ยงต่อการเปลี่ยนชุดน้ำหนัก

## 1.7 ข้อจำกัดและเงื่อนไขของโครงงาน

1. ระบบเป็นต้นแบบสำหรับห้องปฏิบัติการ ผลการประเมินไม่ได้แสดงถึงประสิทธิภาพในระบบใช้งานจริง (production)
2. แบบจำลองความเสี่ยงเป็นแบบจำลองถ่วงน้ำหนักที่ใช้กฎ พัฒนาขึ้นสำหรับสภาพแวดล้อมการทดลองที่ควบคุมได้
   โดยอ้างอิงแนวคิดจาก CVSS และ NIST incident handling แต่**ไม่ใช่คะแนนความเสี่ยงมาตรฐานสากล**
   น้ำหนักและตารางการแปลงค่าเป็นพารามิเตอร์ของการออกแบบการทดลอง
3. คะแนนความเสี่ยงใช้เพื่ออธิบายและบันทึกการประเมิน ส่วนการตัดสินใจตอบสนองเป็นหน้าที่ของ rule engine
   ตามเงื่อนไขที่กำหนดไว้ล่วงหน้า
4. ความสามารถในการตรวจจับขึ้นกับกฎของ Suricata ที่ตั้งค่าไว้ ระบบไม่ได้อ้างว่าตรวจจับการโจมตีได้ทุกชนิด
5. การปิดกั้นอัตโนมัติอาจมีความเสี่ยงต่อการใช้งานเมื่อเกิดผลบวกลวง จึงออกแบบ allowlist และการตรวจสอบการบังคับใช้
   เป็นกลไกควบคุม
6. การกู้คืนมุ่งที่สุขภาพเชิงฟังก์ชันของ Suricata ไม่ใช่การจัดการบริการแบบครบวงจรหรือสถาปัตยกรรม high availability
7. โครงงานไม่ได้วัดเวลาตอบสนองของมนุษย์ จึงไม่ได้อ้างเปอร์เซ็นต์ของเวลาที่ลดลงเมื่อเทียบกับการทำงานด้วยมือ

## 1.8 โครงสร้างของรายงาน

- **บทที่ 2 ทฤษฎีและงานที่เกี่ยวข้อง** — firewall, IDS, EVE JSON, event correlation, การประเมินความเสี่ยง,
  การตอบสนองอัตโนมัติและกลไกความปลอดภัย, การตรวจสุขภาพและกู้คืนบริการ
- **บทที่ 3 การวิเคราะห์และออกแบบระบบ** — สถาปัตยกรรม, การไหลของข้อมูล, แบบจำลองความเสี่ยง, กฎการตัดสินใจ,
  โครงสร้างฐานข้อมูล และกลไกกู้คืน
- **บทที่ 4 การพัฒนาระบบ** — การ implement แต่ละส่วนของ security engine, การตั้งค่า และการทดสอบซอฟต์แวร์
- **บทที่ 5 การทดลองและวิธีประเมินผล** — สภาพแวดล้อม, วิธีป้อนข้อมูล, สถานการณ์ทดสอบ T1–T11 และตัวชี้วัด M1–M10
- **บทที่ 6 ผลการทดลองและอภิปรายผล** — ผลเชิงฟังก์ชัน, ผลการวัด, การวิเคราะห์ความไว, การอภิปราย และข้อจำกัด
- **บทที่ 7 สรุปและข้อเสนอแนะ** — คำตอบของคำถามวิจัย, ข้อสรุป และงานในอนาคต
